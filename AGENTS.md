# Working in this repo

This is `itential/assets` — community-contributed Studio Projects, Automations, Golden Configurations, OpenAPI specs, and LCM Resource Models for the Itential Platform and Itential Gateway.

Before touching any asset, read [`CONTRIBUTING.md`](./CONTRIBUTING.md) (contribution process, PR naming) and [`STANDARDS.md`](./STANDARDS.md) (the actual content rules per asset type). Those two files are the source of truth — this file only adds the mechanical gotchas that are easy to get wrong even after reading them, because they only show up once you're hand-building the JSON.

## Branding

Say "Itential Platform" and "Itential Gateway" (or "Platform"/"Gateway" once introduced, or a version like "P6"/"IG5"). Never "IAP" or "IAG" — both are retired abbreviations, including in old boilerplate you might be copying from an existing README.

## OpenAPI specs

- Every `-latest.json` needs an `x-itential-curated` string in `info`, even when a review found nothing to cut — a missing field means "not yet reviewed," not "nothing to cut."
- When reporting or documenting an operation count, count **path × method pairs**, not unique paths. A path with `get` and `post` is 2 operations, not 1. This repo's existing prose consistently uses the method-count convention — don't introduce the other one.
- Only one `securityScheme` per spec. Split into separate files if the vendor supports incompatible auth methods.
- Studio Project tasks should wire to the `-latest` Integration Model, not a pinned dated version.

## Workflow / Studio Project JSON

These are hand-built JSON files, not generated by the platform UI, so nothing catches a structural mistake until you import it:

- Task IDs are hex-only (`[0-9a-f]{1,4}`).
- `evaluation` operators come from a closed enum (`contains, !contains, <, <=, >, >=, ==, !=`) — no others exist. Every `evaluation` task needs both a success and a failure transition.
- `merge` uses `"variable"` in `data_to_merge`; `childJob` uses `"value"`. Mixing these up fails silently or errors at runtime, not at save time.
- `$var` references don't resolve inside nested objects (e.g. inside a `body` field typed `object`) or inside nested `forEach` bodies — route through a `merge` or `makeData` task first, or use `$var.job.<name>` inside loops.
- For adapter tasks: `app`/`locationType` come from `apps.json`, not `tasks.json` (`tasks.json`'s `app` field is often wrong for adapters). `adapter_id` is the adapter/integration **instance** name for the target environment — never carry over the instance name from a spec or another environment's export.
- For Integration-Model-backed adapters, the task's `response`/`outgoing` value at runtime is the full HTTP envelope (`{ok, url, status, headers, text, body}`) — the real payload is at `response.body`, not the top level.
- Don't assume a task schema or response shape — fetch it (`multipleTaskDetails`) or inspect a real job's resolved task output before wiring dependent tasks to it.

## README structure

- TOC goes right after the intro, before `## Contents`. Fix heading levels first (a section documenting a sibling section's content should be nested under it, not a same-level sibling) — a TOC built before that fix bakes in the wrong structure.
- Don't nest deeper than one level (`##` then `###`) — deeper anchors get fragile on GitHub's slugifier with duplicate/special-character headings.
- When adding or checking a TOC by hand, verify anchors against GitHub's actual slug algorithm (lowercase, strip everything but `[a-z0-9_ -]`, spaces→hyphens, no collapsing, duplicates get `-1`/`-2` suffixes) rather than eyeballing it — small mismatches are easy to miss by inspection.

## General

- Verify claims against the running platform (or the actual JSON) rather than assuming — schemas, response shapes, and operation counts in this repo have drifted from prose before.
- When a change touches many files the same way (a rebrand, a repo-wide column addition), write a small script to apply and verify it rather than editing by hand — and re-run a check pass after, since off-by-one counting mistakes are easy to introduce at scale.
